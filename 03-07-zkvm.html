zkVM 与 zkEVM：把整个虚拟机做成电路

前面所有模块讲的是「怎么证一个函数」。真实系统要证的是一整个程序的执行 —— 几百万条指令、几 GB 内存、还有输入输出。 这一页讲这条从「指令」到「证明」的流水线怎么搭。

工程总装 ≈ 18 min 难度 4 / 5 前置：算术化 · 查找论证 · 递归 代表：RISC Zero · SP1 · Scroll

01这个模块要解决什么问题

你不想为每一个程序都手写一套电路。你想要的是一台通用机器： 把程序喂进去，它输出「执行结果 + 一个证明」。

程序 P + 输入 x  ⟶  输出 y + 证明 π π 证明「存在一次 P(x) 的执行，输出是 y」

这台机器的电路是固定的（只跟指令集有关，跟具体程序无关）。 用户写自己的程序，编译成指令，跑一遍，生成 trace，交给证明系统。

这就是 zkVM 的核心抽象。它把「为每个应用写电路」变成了「写程序」—— 工程门槛降了一个数量级。

i
为什么这件事以前做不到

因为指令执行是状态相关的：下一条执行哪条指令，取决于当前寄存器的值。 电路是固定形状的，没法「跳转」。 解决办法是：不跳转，按顺序执行所有指令，用选择子屏蔽掉不该生效的那些。

02两条路线：复刻 EVM，还是重造一台机器

路线做法优势代价
zkEVM 复刻以太坊虚拟机的语义：256 位栈、gas 计量、存储、预编译 与现有合约完全兼容，开发者零迁移 工程量巨大；gas 语义和存储结构在电路里极难表达
zkVM 用现成指令集（多为 RISC-V），配标准工具链 通用、可用 C/Rust 写程序、工具链成熟 每条指令的约束开销固定，简单程序反而更贵

一句话：zkEVM 是「为兼容性付账」，zkVM 是「为通用性付账」。 前者让 Solidity 直接跑，后者让任何语言都能写。

zkEVM：Solidity → EVM 字节码 → 电路（每个 opcode 一种约束）
zkVM：Rust/C → RISC-V 指令 → 电路（每条指令一种约束）

03zkVM 的架构：四个组件

1

指令集与执行器

定义一个最小的 RISC-V 子集（通常 RV32IM：整数 + 乘法）。 执行器在本地跑一遍程序，记录每一步的完整状态。

2

Trace：状态表

每行是一个时钟周期，列包括：PC、32 个寄存器、指令编码、内存读写地址与值。 一百万条指令就是一百万行。

3

约束系统

两类约束：行内（这条指令的语义，比如 ADD 的输入输出关系）和 跨行（PC 怎么变、寄存器在下一行是否保持、内存读写是否一致）。

4

内存一致性

这是最麻烦的部分。内存不是「一个格子」，而是一堆按时间排序的读写事件。 必须证明：每次读到的值，等于之前最后一次写入的值。

!
内存检查为什么难

朴素做法是「每个读操作，回头看所有历史写操作」—— 复杂度 O(n²)，不可行。 实际做法：把所有读写事件按地址排序，再按时间检查相邻事件。 排序本身要用置换论证或查找表来证明。

04从 trace 到证明：五步

步骤做什么用到的模块
1把 trace 的每一列插值成多项式多项式与 FFT
2把指令语义写成选择子 + 约束算术化（PLONKish）
3用查找表检查 opcode 合法性与位宽查找论证
4用置换论证保证内存/寄存器一致置换论证
5生成证明并递归压缩递归 + 聚合

注意这张表：zkVM 不是新发明，它是前面所有模块的总装。 每一个零件你都见过，难的是让它们在一百万行的规模上协同工作。

一个具体的约束长什么样

以 RISC-V 的 ADD rd, rs1, rs2 为例：

isAdd · ( rd' − rs1 − rs2 ) = 0
isAdd · ( pc' − pc − 4 ) = 0
( 1 − isAdd ) · ( 其他指令的约束 ) = 0 isAdd 是选择子；只有当前行是 ADD 时，前两式才生效

所有指令的约束都写成这种「选择子 × 表达式」的形式，加在一起就是完整的状态转移约束。 这就是 PLONKish 自定义门的典型用法。

05zkEVM 的特殊难点：EVM 不是为电路设计的

EVM 特性为什么在电路里难常见解法
256 位字 域元素也是 256 位左右，加法会溢出，需要额外的范围检查 拆成多个 32 位段，分段约束
gas 计量 每个 opcode 的动态 gas 依赖状态（存储冷热、内存扩展），是数据相关的 把 gas 计算也做成查表 + 约束
Merkle Patricia Trie 状态存储是稀疏默克尔树，路径长度可变 改用固定深度的稀疏树，或承诺整个状态
预编译合约 椭圆曲线运算、哈希，在电路里极贵 为每个预编译写专用子电路
动态跳转 JUMP/JUMPI 的目标地址运行时才知道 把整个代码段做成查找表，用 PC 查指令

这张表解释了为什么 zkEVM 的工程量是 zkVM 的几倍 —— EVM 的每一个设计选择，几乎都和电路的固定形状相冲突。

一个必须知道的数字

zkVM 的证明开销通常是原始执行的 10⁴–10⁶ 倍。 一段跑 1 秒的 Rust 程序，生成证明可能要几十分钟。

执行 1 秒  ⟶  证明 10–60 分钟 这就是为什么 zkVM 目前主要用于「验证」而不是「加速」
!
选型的真实判断

如果你的程序只跑一次、结果要给别人信 → zkVM 合适。
如果你要每秒处理几千笔交易 → 必须用专用电路（zkEVM 或定制）， 因为通用 zkVM 的每指令开销承受不了这个吞吐。

07小结与常见误区

你应该带走的

  • zkVM 把「为每个应用写电路」变成「写程序」，电路只跟指令集有关。
  • 核心是 trace：每行一个时钟周期，记录 PC、寄存器、内存读写。
  • 内存一致性靠「按地址排序 + 相邻检查」，不是逐个回看历史。
  • zkEVM 的难点在于 EVM 的每个设计都和固定电路冲突。
  • zkVM 不是新发明，它是算术化 + 查找 + 置换 + 递归的总装。
✕「zkVM 可以加速程序执行。」
✓
完全相反。证明开销是原始执行的 10⁴–10⁶ 倍。 zkVM 的价值是让别人相信结果，不是让程序跑得更快。
✕「zkEVM 比 zkVM 更高级。」
✓
两者是不同的取舍：zkEVM 换兼容性，zkVM 换通用性。 做一个新应用，zkVM 往往更快落地；要让现有 Solidity 合约无痛迁移，只能 zkEVM。
✕「trace 里存了所有状态，所以证明者能还原我的输入。」
✓
trace 是证明者本地的数据，不会上传。上链的只有证明和公开输入。 但要注意：如果 trace 被日志记录或上传到云端，隐私就泄露了。
✕「指令集越小，证明越快。」
✓
指令集小意味着每条指令的约束更通用，但完成同样功能需要更多指令。 总开销 = 指令数 × 每条约束数，两者要平衡。RISC-V 的 RV32IM 是当前的经验最优点。
