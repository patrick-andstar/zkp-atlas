电路审计：唯一不能省的成本

密码学保证了「你证明了你说要证的东西」，但没有任何机制保证 「你说要证的东西就是你想证的东西」。 这条缝隙里，埋着 ZKP 领域绝大多数真实事故。

安全底线 ≈ 16 min 难度 4 / 5 前置：电路 DSL · 算术化 产出：可上线的电路

01为什么这件事不能靠「跑通了」

普通程序出错，通常会有异常、崩溃、日志、测试失败。 电路出错什么都不发生：编译通过、证明生成、链上验证通过。

检查手段能发现约束不足吗
编译不能（语法完全合法）
单元测试不能（正常输入下行为正确）
证明生成不能（会成功生成）
链上验证不能（会通过）
对抗性输入 + 形式化分析能

所以审计不是「最佳实践」，是唯一的发现手段。 这也是为什么成熟团队愿意在审计上花几十万美元 —— 不是合规要求，是没有别的办法。

02约束不足：一个能跑通的漏洞

看一段「看起来完全正常」的 Circom 代码。它要实现：给定 x，输出 x²， 并检查 x 不为零。 

template Square() {
    signal input x;
    signal output y;
    signal invX;

    y <== x * x;              // 正确：赋值 + 约束

    invX <-- 1 / x;           // 只赋值，没有约束！
    // 缺少: invX * x === 1;
}

这段代码在「诚实输入」下完全正确：x = 3 时 y = 9， invX = 1/3，证明能通过。

但证明者可以这样做：

公开输入 x = 0   （本应被拒绝）
令 invX = 12345   （任意值）
y = 0   ✓ 约束 y = x² 满足
没有约束检查 invX，所以整个电路通过

「除以零」这个本应被拒绝的情况，被悄悄放行了。 如果这个 invX 后续被用于计算利率、份额、清算价格 —— 后果可想而知。

!
这类 bug 的共同特征

正常路径下行为正确，异常路径下静默通过。 测试通常只覆盖正常路径，所以永远发现不了。

03三类高发漏洞

第一类：只赋值不约束

最常见。多发生在用 <-- 的地方：位分解、除法、比较、查表索引。 每一个 <-- 都必须能找到一条配套的 ===， 否则就是一个自由变量。

第二类：位宽检查不完备

域元素是 254 位，没有「溢出」概念。想让一个值表示 u32， 必须显式约束 0 ≤ x < 2³²。少检查一位，攻击者就能塞进 2³² 以上的值。 

// 错误：只检查了 31 位
for (var i = 0; i < 31; i++) { ... }

// 正确：32 位全查
for (var i = 0; i < 32; i++) { ... }

第三类：公开输入未绑定

电路算对了，但验证合约没有把关键值作为公开输入传进去。 于是攻击者可以拿一份合法证明，配一个伪造的公开输入去验证。

场景漏掉的绑定后果
Rollup新的状态根可任意「更新」状态
跨链桥目标链 ID证明可跨链重放
空投接收者地址可把份额转给自己
i
这类 bug 不在电路里，在「接线」上

电路本身可能完全正确，审计电路发现不了。必须同时审计验证合约的调用方式： 哪些参数传了，哪些没传，顺序对不对。

04形式化验证：把「有没有漏约束」变成可判定问题

约束不足的本质是：存在两组不同的见证，都能满足全部约束，但语义不同。 这在数学上可以精确表述，也就可以自动检查。

工具做什么适用
Ecne 以太坊基金会出品，把 Circom 电路转成 SMT 公式，检查是否存在「约束不足」 中小规模 Circom 电路
Civer ConsenSys 出品，类似思路，输出反例 Circom
circomspect 静态分析器，检查常见模式（未约束信号、可疑的 <--） 快速筛查
Lean / Coq 手工写机器证明，验证电路语义 核心协议、成本极高

Ecne 的输出长什么样

它不只是说「有问题」，而是给出两组不同的见证： 它们在所有约束下都合法，但产生不同的输出。这两组见证就是漏洞的直接证据。

见证 A：x = 0, invX = 1, y = 0   ✓ 通过
见证 B：x = 0, invX = 999, y = 0   ✓ 通过
同一公开输入，不同私密输入，都合法 —— 这就是约束不足
!
形式化验证的局限

它只能检查「约束是否唯一确定见证」，不能检查 「约束是否表达了你的业务意图」。 如果电路逻辑本身就写错了（比如把「大于」写成「小于」），工具会说「约束很完备」，然后你上线一个错误系统。

05差分测试与模糊测试：工程手段

差分测试：同一逻辑，两种实现

用普通语言（Rust / Python）实现一遍同样的业务逻辑，然后随机生成输入， 比对两边输出是否一致。

随机输入 x  ⟶  电路输出 ycircuit
               ⟶  参考实现 yref
断言 ycircuit = yref 参考实现可以用任何语言，只要能表达业务逻辑

这能发现「逻辑写错」类问题，但发现不了「约束不足」—— 因为参考实现和电路在正常输入下行为一致。

模糊测试：专门找异常路径

不同于随机输入，模糊测试专门构造边界值和恶意值：

  • 0、1、p−1（域的最大值）
  • 232−1、232（溢出边界）
  • 数组索引越界、Merkle 路径长度为 0
  • 同一变量在多个位置赋不同值（专门打约束不足）
✓
一个有效的土办法

写一个「恶意证明者」脚本：故意让某个 <-- 变量的值偏离正确计算， 然后看证明能不能通过。如果能通过，说明那个变量没被约束。 这个测试比任何静态分析都直接。

06审计清单：逐条过

#检查项怎么查
1每个 <-- 是否都有配套的 ===grep 全部 <--，逐个核对
2每个 signal 是否至少出现在一条约束里静态分析 / 编译器警告
3所有位宽检查是否覆盖完整位宽数循环次数
4除法是否处理了除零找所有 1/x 和 /
5数组访问是否越界检查索引的约束范围
6公开输入是否全部绑定到验证合约对比电路 signal 与合约参数
7是否有「永远为真」的约束（如 x*0 === 0）形式化工具会标记
8常量是否正确（尤其是位掩码、模数）单元测试 + 人工核对
9是否复用了不该复用的信号代码审查
10电路与验证合约的 vk 是否匹配重新编译比对哈希

07小结与常见误区

你应该带走的

  • 约束不足是头号杀手：编译、测试、证明、验证全都发现不了。
  • 每个 <-- 都必须有配套约束，否则就是自由变量。
  • 三类高发：只赋值不约束、位宽检查不全、公开输入未绑定。
  • 形式化验证（Ecne / Civer）能自动找约束不足，但查不出业务逻辑错误。
  • 差分测试查逻辑，模糊测试查边界，两者互补。
✕「测试覆盖率 100% 就说明电路没问题。」
✓
覆盖率衡量的是「代码被执行过」，不是「约束完备」。 一个约束不足的电路，在 100% 覆盖率下依然完全正常 —— 因为正常输入本来就不会触发漏洞。
✕「形式化验证通过就万事大吉。」
✓
它只证明「约束唯一确定见证」，不证明「约束符合业务意图」。 把业务需求翻译成约束这一步，仍然只能靠人。
✕「审计一次就够了。」
✓
电路改一行就要重新审计。很多事故发生在「小改动」之后 —— 因为改的人以为只是加个功能，实际上破坏了某条约束的完整性。
✕「用成熟的库就不会有电路漏洞。」
✓
库只保证底层原语正确。漏洞几乎总是出在「你怎么用」 —— 漏了一条约束、传错一个参数、少检查一位。这些是业务代码的问题，库管不了。
