哈希与随机预言机：那个「假装随机」的假设

Fiat–Shamir 用哈希生成挑战，Merkle 树用哈希承诺数据，STARK 用哈希替代配对。 整个 ZKP 到处是哈希 —— 但「哈希像随机函数」这件事，是一个假设，不是定理。

≈ 12 min 难度 2 / 5 前置：无 被用于：Fiat–Shamir · FRI · Merkle

01这个模块要解决什么问题

哈希在 ZKP 里不是「加密」，也不是「压缩」。它承担三个完全不同的职责，混起来容易糊涂。

职责怎么用用在哪
生成挑战 把「承诺 + 公开输入」映射成一个随机数 Fiat–Shamir
承诺数据 把一大块数据压成一个摘要，改一位就变 Merkle 树、FRI
抗碰撞标识 给电路、验证密钥、协议版本打指纹 域分隔、防重放

三者共用一个前提：给定输入，输出看起来完全随机；但同样的输入必然得到同样的输出。 这个「确定性 + 随机性」的组合，是哈希全部魔力的来源。

02三条安全性质，强度依次递减

抗原像：给定 h，找 x 使 H(x) = h 不可行
抗第二原像：给定 x，找 x' ≠ x 使 H(x') = H(x) 不可行
抗碰撞：找任意一对 x ≠ x' 使 H(x) = H(x') 不可行
性质攻击复杂度ZKP 里靠它做什么
抗原像2n承诺的隐藏性（不能从摘要反推数据）
抗第二原像2n绑定性（不能换一个同样摘要的值）
抗碰撞2n/2（生日攻击）整体一致性（Merkle 根、电路指纹）

注意抗碰撞只有 2n/2：SHA-256 的碰撞强度是 128 位，不是 256 位。 所以在要求「128 位安全」的系统里，SHA-256 刚好够，不能打折。

i
ZKP 里最常用的是哪一条

主要是抗碰撞（Merkle 树、FRI 的一致性）和抗原像（承诺的隐藏性）。 抗第二原像用得少，但在「防重放」场景里会出现。

03随机预言机模型：一个必须说清的假设

安全性证明里，我们常常把哈希 H 当成一个真正的随机函数： 对任何新输入，输出均匀随机，且与之前所有输出无关。这个理想化的对象叫随机预言机（RO）。

H : {0,1}* → {0,1}λ   （理想化为真随机） 任何人都可以查询，但输出不可预测；同样的输入永远得到同样的输出

在 ROM 下，Fiat–Shamir 的安全性可以严格证明：证明者要作弊，必须在查询哈希之前 猜中它的输出，概率是 2−λ。

但真实哈希不是随机函数

SHA-256 有固定结构（Merkle–Damgård），有长度扩展性质，有已知的分析方法。 它看起来像随机函数，但没人能证明它真的像。

!
这意味着什么

「SNARK 在 ROM 下安全」不等于「SNARK 在实际中安全」。中间隔着一层假设： 你用的哈希确实行为像随机函数。 历史上出现过「在 ROM 下安全、但用具体哈希实现后被攻破」的协议（比如某些签名方案）。

工程上的应对：用经过充分分析的标准化哈希（SHA-256、SHA-3、BLAKE3）， 不要自己设计，也不要用被弱化的变体。

04Merkle 树：用哈希承诺一整张表

FRI 需要承诺「一个多项式在上百万个点的取值」。直接哈希整张表，验证者没法查单个位置。 解法是分层哈希：

1

叶子层

每个数据块单独哈希：leafi = H(datai)。

2

逐层向上

相邻两个哈希拼接再哈希：node = H(left ‖ right)，直到只剩一个根。

3

打开某个位置

给出 datai 和从叶子到根的 log n 个兄弟哈希。 验证者逐层重算，看是否等于根。

证明大小 = O(log n) 个哈希   |   验证时间 = O(log n) 次哈希 改任何一个叶子，根都会变 —— 这是绑定性

FRI 的证明里，绝大部分字节都是 Merkle 路径。这也是 STARK 证明比 SNARK 大的直接原因： 它用 log n 条路径替代了一次配对。

i
一个容易忽略的细节

哈希 H(left ‖ right) 里的拼接必须无歧义。 如果 left 和 right 长度可变，不同的树结构可能产生相同的字节串。 标准做法是固定长度，或者加域分隔符。

05ZK-friendly 哈希：为什么不用 SHA-256

这是个反直觉的工程事实：SHA-256 在电路里极其昂贵。

SHA-256 是位运算的堆叠：移位、异或、与、旋转。每个 32 位字要 64 轮。 把它翻译成算术电路，需要把每个比特拆开单独约束 —— 一次 SHA-256 约 2–3 万条约束。

哈希电路约束数（约）设计取向
SHA-25620,000–30,000为 CPU 优化（位运算快）
Poseidon~200–400为算术电路优化（只用加法和乘方）
Rescue / Rescue-Prime~300–500同上，安全性论证更保守
MiMC~100–200最简单，但安全性边界较窄

差距是两个数量级。所以 ZK 系统内部几乎都用 Poseidon 这类「代数哈希」， 只在需要与外部世界交互时（比如验证以太坊签名）才用 SHA-256。

!
代价：安全分析历史短

Poseidon 2019 年才提出，密码分析历史远不如 SHA-256 的二十年。 已经出现过针对简化轮数的攻击，实际部署需要留足安全余量（多跑几轮）。 「快」和「被充分研究」在这里是矛盾的。

06长度扩展与域分隔：两个真实的坑

坑一：长度扩展攻击

SHA-256 用 Merkle–Damgård 结构：H(m) 的输出就是处理完 m 后的内部状态。 所以知道 H(m) 的人，可以在不知道 m 的情况下算出 H(m ‖ pad ‖ m')。

给定 H(m)  ⟹  可以算出 H( m ‖ padding ‖ m' ) 这在「把哈希当 MAC 用」时会致命，但在承诺场景里通常无害（因为攻击者改不了原文）

防御方式很标准：用 HMAC，或者用 SHA-3/BLAKE3 这类不具长度扩展性的结构。

坑二：transcript 缺少域分隔

如果两个不同协议用同样的方式构造挑战，攻击者可以把 A 协议的证明搬到 B 协议里。 防御方式是在哈希输入里加入协议标识和版本号：

c = H( "my-protocol-v1" ‖ vk ‖ x ‖ R ) 任何一个字节不同，挑战就完全不同
✓
一句话原则

凡是你不想让它们互相替换的东西，都要进哈希。 协议名、版本、验证密钥、公开输入、所有承诺 —— 少一个就是一个攻击面。

07小结与常见误区

你应该带走的

  • 哈希在 ZKP 里干三件事：生成挑战、承诺数据、打指纹。
  • 三条性质强度递减：抗原像 2n、抗第二原像 2n、抗碰撞 2n/2。
  • 随机预言机是假设，不是定理。安全性证明都在这个模型下。
  • Merkle 树用 O(log n) 的路径承诺 O(n) 的数据。
  • Poseidon 比 SHA-256 快两个数量级，因为它是为算术电路设计的。
✕「哈希是加密的一种。」
✓
哈希不可逆，没有密钥，也不打算还原原文。加密是可逆的，有密钥。 两者目标完全相反。
✕「SHA-256 有 256 位安全。」
✓
碰撞强度只有 128 位（生日攻击）。 如果说「256 位安全」，指的是抗原像/第二原像。
✕「用了哈希就自动零知识。」
✓
哈希只提供「绑定性」和「伪随机性」。零知识需要模拟器， 那是协议结构的事，不是哈希能给的。
✕「ZK-friendly 哈希更快，所以应该全面替换 SHA-256。」
✓
只在电路内部更快。与外部系统交互（签名验证、TLS、区块链头）必须用标准哈希， 否则没人能验证你的数据。
