证明后端：真正干活的那一层

DSL 负责「描述电路」，后端负责「把电路变成证明」。同一个电路换后端， 证明时间可能差三倍，证明大小可能差三个数量级。 选后端不是选语言，是选一整套密码学与工程假设。

≈ 14 min 难度 3 / 5 前置：证明系统 产出：可跑的证明服务

01后端到底负责什么

一个完整的证明系统有五个零件：算术化、承诺、挑战生成、证明组装、验证。 后端就是把这五个零件实现出来的那个库。

零件后端提供什么
域运算大数模运算、逆元、FFT/NTT
椭圆曲线点加、标量乘、MSM、配对
多项式承诺KZG / FRI / IPA 的承诺与打开
证明协议Groth16 / PLONK / STARK 的完整流程
序列化证明的压缩编码、链上格式

看起来只是「实现细节」，但这些细节的性能差异极大。 同样是 MSM（多标量乘），一个优化过的实现比朴素循环快 50 倍以上。

02五个主流库，各自的定位

库语言支持的证明系统特点
arkworksRust Groth16、Marlin、Groth16 模块化程度最高，像「密码学乐高」。学习曲线陡，但改协议最方便
gnarkGo Groth16、PLONK API 友好，内置电路库，以太坊生态集成好
halo2Rust PLONKish（IPA / KZG） zkEVM 的事实标准，支持自定义门和查找表。API 极低层
plonky2 / 3Rust FRI-based（非配对） 证明速度极快（Goldilocks 域 + 小域），但证明较大
snarkjsJS Groth16、PLONK 浏览器里就能跑，适合原型和教学。性能不是它的目标
i
「支持更多证明系统」不等于更好

arkworks 支持很多协议，但每个都不是最快的。halo2 只支持 PLONKish， 但在 zkEVM 场景下是最优的。专用永远打败通用，这是工程领域的常态。

03评价一个后端，看这五个数

指标怎么测典型量级（百万约束）
证明时间端到端跑 10 次取中位数10–60 秒
峰值内存监控 RSS，注意是峰值不是平均2–16 GB
证明大小序列化后的字节数128 B – 200 KB
验证成本链上 gas，或本地毫秒数20 万 – 200 万 gas
设置开销是否需要仪式、需要多大分钟到小时

一个常被忽略的指标：内存

证明者的内存占用通常是电路规模的 3–10 倍（以域元素计）。 一个 100 万约束的电路，可能有 8 GB 峰值内存。 在云上跑，这会直接决定你用什么规格的机器 —— 以及每小时多少钱。

!
benchmark 要看「同电路同参数」

论文和博客里的「快 3 倍」经常是在不同电路、不同安全参数下测的。 真正可比的基准是：同一条电路、同一个域、同一个安全级别。 自己跑一遍最靠谱。

04抽象层次：你在哪一层工作

高层   Cairo / Noir  —— 写业务逻辑，编译器管约束
中层   Circom + snarkjs  —— 手写约束，工具链管仪式
低层   Halo2 / arkworks  —— 直接操作表格和多项式

层次越低，可控性越强，但开发成本呈指数上升。一个具体的对比：

任务Circom 代码量Halo2 代码量
简单乘法约束~10 行~80 行（要配列、门、选择子）
Merkle 路径验证~40 行~300 行
完整 zkEVM不现实数万行 + 多人年
i
为什么 zkEVM 都用 Halo2

因为 EVM 有大量「查表」语义（opcode 分发、内存读写、栈操作）， 这些在 Circom 的 R1CS 里表达极差，在 PLONKish 的查找表里却很自然。 不是 Halo2 更快，是它更能表达这个东西。

05性能从哪来：两个热点

不管用哪个后端，证明时间基本都花在两个操作上：

MSM（多标量乘）：Σ aiPi   ← 占 50–70%
NTT（数论变换）：多项式点值 ↔ 系数   ← 占 20–40%

MSM 为什么这么贵

朴素做法是 n 次标量乘再加起来，复杂度 O(n·log p)。 Pippenger 算法把它降到 O(n / log n)，常数因子仍然很大。 一个 100 万点的 MSM，在单核上要几十秒。

优化手段，按效果排序

手段加速比代价
更好的 MSM 算法（Pippenger + 分批）5–20×实现复杂度
多线程（8–32 核）6–25×需要大内存带宽
GPU（CUDA）10–50×显存限制、数据传输
FPGA / ASIC50–200×开发成本极高、不灵活

注意这些加速可以叠加：好的算法 + 32 核 + GPU，比朴素单线程快几百倍。 这也解释了为什么不同团队的「同一条电路」能差出两个数量级。

06怎么选：三个问题

1

你的验证者在哪？

链上 → 必须考虑 gas，选 Groth16（arkworks / gnark / snarkjs）。
链下服务 → 可以选 FRI-based，证明大但生成快。

2

你的电路需要查找表吗？

需要（zkEVM、复杂状态机）→ Halo2 或 Plonky3。
不需要（简单算术）→ Circom 足够，生态最成熟。

3

你能接受多大的工程投入？

小团队、快速验证 → Noir / Circom + snarkjs。
有密码学工程师、要长期维护 → Halo2 / arkworks，把控制权握在手里。

✓
一条务实的路径

先用 Circom 把业务跑通，再考虑换后端。 因为 90% 的时间会花在「电路写对」而不是「证明跑快」上。 等到约束数稳定、瓶颈明确，再针对性优化，比一开始就纠结后端划算得多。

07小结与常见误区

你应该带走的

  • 后端 = 域运算 + 曲线 + 承诺 + 协议 + 序列化的完整实现。
  • arkworks 通用、gnark 好用、halo2 强表达、plonky 快、snarkjs 轻。
  • 五个评价指标：证明时间、峰值内存、证明大小、验证成本、设置开销。
  • 性能热点是 MSM 和 NTT，优化可以叠加到几百倍。
  • 先用高层工具跑通业务，再根据瓶颈下沉。
✕「换个更快的后端就能解决性能问题。」
✓
如果电路本身有冗余约束（比如用 16 条约束做一个本可以 1 条查表完成的检查）， 换后端只能带来常数级改善，优化约束才是数量级的。
✕「Rust 库一定比 Go 快。」
✓
语言不是决定因素，算法实现和并行策略才是。 gnark 在 Groth16 上的性能与 Rust 实现相当，因为它同样用了 Pippenger + 多线程。
✕「benchmark 说 3 秒，我的机器上也应该是 3 秒。」
✓
取决于核数、内存带宽、是否开 AVX、电路结构（约束分布）。 差 5–10 倍很正常。一定要在自己的目标机器上实测。
✕「后端库越新越好。」
✓
密码学库的审计历史和稳定性比版本号重要。 一个三年没更新但被反复审计的库，比一个每月发版的实验性库更值得信任。
