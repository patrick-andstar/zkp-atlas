Fiat–Shamir：把「你问我答」变成一条消息

几乎所有零知识协议最初都是交互式的：验证者抛一个随机挑战，证明者回应。 但区块链上没有「现场」—— 证明必须是一条静态消息。 Fiat–Shamir 用一个哈希函数，把「别人随机问你」变成了「自己随机问自己」。

关键转换 ≈ 14 min 难度 2 / 5 前置：哈希 · 承诺 后续：所有非交互证明

01这个模块要解决的问题

交互式零知识证明有一个硬性前提：验证者必须在场。 他要现场生成一个随机数，证明者当场回应。这个来回至少要三轮。

这在三种场景下直接失效：

  • 上链：智能合约不能「暂停等你说完」。交易一旦提交就是终局。
  • 转发：Alice 的证明想给 Bob 看，但 Bob 没参与当时的挑战生成，凭什么相信？
  • 异步：证明生成和验证可能相隔几天，中间没有人保持会话。

所以需要一种方法，把「验证者的随机挑战」替换成某种证明者自己算得出来、但无法预测、也无法事后更改的东西。

i
这个需求听起来像悖论

「自己生成随机数」本来是可以作弊的 —— 证明者可以反复试，直到随机数对他有利。 关键在于：挑战必须由「已经固定下来的承诺」唯一决定， 而承诺一旦发出就改不了。哈希函数恰好提供了这种「先锁后揭」的性质。

02直觉：把骰子换成「封在胶囊里的骰子」

交互式协议里，骰子是验证者掷的。证明者不能控制结果，所以他必须真的能应对任意挑战。

现在换一种玩法：证明者先把所有承诺写在一张纸上，把纸放进保险箱， 然后根据这张纸的内容算出一个数 —— 这个数就是挑战。

为什么这算「随机」？因为纸上的内容是他早就定死的，他没法为了让挑战好看而改纸。 而哈希函数的输出看起来完全随机，他也没法预测。

c = H( 所有公开信息 ‖ 所有承诺 ) c 就是「挑战」。它由哈希算出，不由任何人掷骰子

核心直觉：哈希把「时间」压进了「值」里。 你先承诺、后算挑战，这个顺序被哈希函数强制住了 —— 改了承诺，挑战就变，之前的应答全部作废。

03先看一个最干净的交互式协议：Schnorr

Schnorr 协议用来证明「我知道 x，使得 X = gx」。 它只有三步，是所有 Fiat–Shamir 讲解的标准载体。

1

承诺（Commitment）

证明者随机取 r，计算 R = gr，发给验证者。

作用：把 r 锁死。之后他不能改 r，否则 R 对不上。

2

挑战（Challenge）

验证者随机取 c ∈ 𝔽p，发回去。

作用：引入证明者无法预测的随机性。这是零知识性和可靠性同时成立的关键。

3

应答（Response）

证明者计算 s = r + c·x mod p，发给验证者。

作用：把「我知道 x」这件事编码进一个标量里，同时被 r 盲化，不泄露 x。

验证者检查：

gs = R · Xc 左边 = gr+cx；右边 = gr·gcx。显然相等

为什么这能证明「知道 x」？因为要构造出通过验证的 s，必须同时满足 s = r + c·x —— 而 c 是验证者临时给的，证明者无法预知， 所以只能真的知道 x 才能算出 s。

✓
三个性质各由什么保证

完备性：代数恒等式，必然成立。
可靠性：c 随机，猜中的概率是 1/p。
零知识：s 被 r 盲化，给定 s 反推 x 等价于解离散对数。

04变换：三步变成一步

把上面的协议改写，只做一件事 —— 把「验证者随机取 c」换成「哈希算 c」。

变换前（交互式，3 轮）

轮次发送方内容
1Prover → VerifierR = gr
2Verifier → Proverc ← 𝔽p（真随机）
3Prover → Verifiers = r + c·x

变换后（非交互，1 条消息）

证明者本地计算：
  R = gr
  c = H( g, X, R )   ← 关键：c 由 R 决定
  s = r + c·x
然后发送三元组 π = ( R, s ) 验证者拿到 π 后，自己重算 c = H(g, X, R)，再检查 gs = R·Xc

整个过程不再需要验证者在线。证明变成了一条可转发、可存储、可上链的消息。

为什么这不是「自己出题自己答」

表面上看，证明者确实同时在扮演两个角色。但关键在于：他只能在承诺之后才知道题目。

假设他想作弊 —— 随便挑一个 s，然后反推一个能通过验证的 R。 他需要 R = gs·X−c，而 c = H(g,X,R) 又依赖 R。 这是一个自指方程：c 由 R 决定，R 又由 c 决定。 要解开它，就得找到一个哈希的不动点 —— 这被当作计算上不可行。

i
这就是「随机预言机」假设

严格的安全性证明要求把 H 建模成一个真正的随机函数： 对任何新输入，输出均匀随机、不可预测。真实哈希只是它的近似。 在这个模型下，证明者要作弊，等价于在查询哈希之前就猜中它的输出。

05安全性到底来自哪里

Fiat–Shamir 不是一个「免费的转换」。它的安全性依赖两个前提，缺一不可。

前提一：哈希被建模为随机预言机

如果哈希有结构性弱点（比如输出分布不均、能找到碰撞），挑战就可能被预测或操纵。 现实中我们假设 SHA-256、Poseidon 这类函数足够接近随机预言机 —— 但这是假设，不是定理。

前提二：挑战绑定了一切该绑定的东西

这是实现层面的事，也是事故高发区。挑战必须覆盖：

必须绑定的为什么
所有公开输入否则攻击者可以换一个对自己有利的 statement，复用同一份证明
所有承诺否则承诺与挑战脱钩，可以事后构造
协议标识 / 域分隔符否则跨协议重放（把 A 协议的证明用在 B 协议）
验证密钥否则跨电路重放

形式化地说，transcript 必须满足：改变其中任何一项，挑战都会变。 这通常通过把所有内容按固定顺序序列化后一次性哈希来实现。

06transcript 该怎么构造

一个正确的 transcript 通常是这样的累积结构：

t0 = H( 协议名 ‖ 验证密钥 ‖ 公开输入 )
t1 = H( t0 ‖ 承诺1 )  ⟹  c1 = t1
t2 = H( t1 ‖ 承诺2 )  ⟹  c2 = t2
…… 链式哈希：每一个挑战都继承了之前所有信息，改任何一环都会导致后续全变

这种「链式」结构的好处是：不需要每次都把所有历史重算一遍，只需要把上一个哈希值带进来。 成本是 O(1)，安全性是「全历史绑定」。

!
最常见的实现错误

只哈希了「承诺」，忘了哈希「公开输入」。后果是：攻击者可以拿一份合法证明， 换一个公开输入去验证 —— 因为挑战没变，证明依然通过。 在 Rollup 里，这等于可以伪造任意状态根。

07Frozen Heart：真实发生过的事故

2022 年 4 月，Trail of Bits 披露了一类影响多个零知识证明库的漏洞，命名为 Frozen Heart。 它不是数学问题，是transcript 绑定不全的实现问题。

漏洞形态

某些实现里，生成挑战时只哈希了部分承诺，漏掉了另一些公共参数。 攻击者于是可以：

  1. 固定住挑战 c（因为影响它的输入没变）；
  2. 反复调整未被绑定的那些参数，直到证明通过；
  3. 由于 c 不变，原本应该「每个证明只能试一次」的限制失效了。

正常协议里，猜错一次挑战就作废，攻击成功率是 1/p。 但挑战固定之后，可以无限次试错，成功率变成 1。

影响范围

Bulletproofs 的多个实现、若干 PLONK 变体、以及一些自研的 SNARK 库受影响。 修复方式很简单：把该绑定的全部绑进 transcript。 但发现问题花了很久，因为所有测试都通过 —— 数学是对的，只是输入少了。

!
教训

Fiat–Shamir 的安全性完全取决于 transcript 的完整性。 这不是「顺手加个哈希」的事，每一处遗漏都是一个可被放大的攻击面。 审计时应该问：「如果把任何一个公开值改掉，挑战会变吗？」

08小结与常见误区

你应该带走的

  • Fiat–Shamir 把「验证者掷骰子」换成「哈希算挑战」，交互式变非交互式。
  • 安全性依赖：哈希 ≈ 随机预言机 + transcript 绑定完整。
  • 证明者不能作弊，因为挑战依赖承诺，而承诺已经锁死 —— 自指方程无法解开。
  • 典型三元组：(R, s)，验证者重算 c = H(g,X,R) 后检查 gs = R·Xc。
  • Frozen Heart 证明：漏绑一个公开值，就能让攻击从 1/p 变成 1。
✕「Fiat–Shamir 只是把随机数换成哈希，很平凡。」
✓
它是一个有安全性证明的变换，但证明在随机预言机模型下才成立。 而且工程上极易出错 —— 过去五年里这类漏洞反复出现，不是「平凡」能形容的。
✕「哈希一下整个证明就行了。」
✓
顺序很重要。必须先有承诺、再算挑战、最后算应答。 如果先算应答再哈希，承诺就失去约束力，攻击者可以构造出通过验证的假证明。
✕「用了 Fiat–Shamir 就不需要可信设置了。」
✓
两件完全不同的事。Fiat–Shamir 解决「交互」，可信设置解决「公共参数怎么来」。 Groth16 两者都需要；STARK 只要前者。
✕「挑战可以随便取，只要看起来随机。」
✓
挑战必须不可预测且不可重放。用固定值、时间戳、区块号当挑战， 都可能被攻击者提前知道并针对性地构造承诺。
