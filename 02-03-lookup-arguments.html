查找论证：把 65536 次比较压成一次查表

在电路里判断「这个数在 0 到 65535 之间」，用传统方法要拆成 16 个比特、加 16 条约束。 查找论证把它变成一句话：这个值出现在这张公开的表里 —— 一条约束都不用加。

≈ 16 min 难度 4 / 5 前置：多项式承诺 · 置换 · 00 · 01 多重集 后续：zkEVM 的 opcode 表

01这个模块要解决什么问题

R1CS 只认加法和乘法。所有「非算术」的操作 —— 比较大小、位运算、查 ASCII 表、 验证某个 opcode 合法 —— 都必须拆成算术约束，成本高得离谱。

看一个具体数字。要约束 x ∈ [0, 216)：

方法约束条数说明
逐位分解16 条拆成 16 个比特，每个比特约束 b(b−1)=0，再加权求和
范围检查（8 位表）2 次查找拆成高低字节，各查一次 256 项的表
直接查 65536 项表1 次查找表本身是公开的，不占约束

在 zkEVM 里，这个差距被放大到决定性：一条 EVM 指令要检查 opcode 合法性、栈高度、 内存偏移范围…… 如果每个都逐位分解，一个区块的证明时间会从分钟级涨到小时级。

i
一句话定位

查找论证是表达力的放大器。它让电路可以「引用」一张预先算好的表， 而不必把表的逻辑重新实现一遍。PLONKish 之所以能跑 zkEVM，靠的就是它。

02直觉：我不是算出来的，我是查出来的

你要证明 x = 4271 满足 0 ≤ x < 65536。与其证明不等式， 不如说：「4271 出现在这张 0…65535 的表里，第 4272 行就是它。」

验证者不需要重新算一遍不等式，只需要确认两件事：① 表是公开且正确的；② 你确实查了表，没瞎编。 第 ① 件由协议约定，第 ② 件才是查找论证要解决的问题。

为什么「查了表」需要证明

如果证明者只是口头说「我查了」，他可以撒谎。所以需要把「查表」这个动作变成一个代数关系： 我提供的所有值，作为多重集，必须是那张表的子多重集。

f = ( f1, f2, …, fn )  ⊆  t = ( t1, t2, …, td ) f 是「被查的值」，t 是「公开的表」。每个 fi 都必须等于某个 tj

注意是多重集：同一个值可以查多次，所以 f 里允许重复。

03数学工具：怎么证明两个多重集相等

整套查找论证建立在一个非常简单的观察上：比较两个集合，不必逐个比对元素， 只要比较它们的「随机指纹」。

指纹：对每个元素加随机数再连乘

给定两个多重集 A、B，取随机挑战 α，定义：

Z(A) = Πa∈A ( a + α )     Z(B) = Πb∈B ( b + α ) 如果 A 和 B 是同一个多重集，两个乘积必然相等

反过来，如果 A ≠ B，那么 Z(A) = Z(B) 的概率极低。 因为差值 Z(A) − Z(B) 是关于 α 的多项式，次数不超过 |A|+|B|， 它在随机点上为零的概率不超过 (|A|+|B|)/p。而 p ≈ 2254，可以忽略。

i
这一步用的是 Schwartz–Zippel 引理

一个非零的 d 次多项式，在 𝔽p 上最多有 d 个根。 所以随机取一个点，踩中根的概率 ≤ d/p。 这就是「随机点验一次 = 验了全部」的严格依据。

从「相等」到「包含」

但我们要证的是 f ⊆ t，不是相等。技巧是补一个 s： 把 f 和 t 合并后排序，得到长度为 n + d 的序列 s。

s = sort( f ∪ t )   ∈   𝔽n+d s 把「表」和「被查值」混在一起，接下来靠相邻关系重新对齐

不要把 s 当成整体去比，而是把它和 (t, f) 交错成两行。 交错之后，每一列的约束都在说同一件事：

si = tj   或   si = tj+1 s 的每一项，要么落在某个表项 tj 上，要么落在这个表项的下一个

如果 f 里所有值都来自 t，排序后每个值都能找到自己的位置，这套交错关系处处成立。 一旦混入表外的值 y，它排序后必然挤在两个表项之间，而这两个表项在 t 里是相邻的 —— 交错关系在那里断裂，无法满足。

i
为什么强调「多重集」而不是「集合」

f 里同一个值可以出现很多次（比如同一个内存地址被读一百次）。 判定单位是带重数的多重集：不仅要「这个值在表里」， 还要「它出现的次数和对面计数对得上」。这就是累乘/倒数和要给每个元素单独一项的原因。

04Plookup：把四个序列串起来

Plookup（Gabizon–Williamson 2020）是目前最经典的查找论证。它的核心是把 「s 与 (t, f) 交错对齐」和「两者的多重集相等」 这两个陈述，用一个累乘多项式同时证明。

四个序列

序列长度含义
fn被查的值（来自电路中的信号）
td公开的表（如 0…255）
sn + df ∪ t 排序后的结果
h1, h2n + d把 f、t、s 交错排列后的两个辅助序列

交错排列的规则

把这三个序列摊成两行，让每一列满足「h1 的相邻两项来自 s， h2 的相邻两项来自 f 或 t」：

h1 = ( s1, s2, …, sd, sd+1, …, sd+n )
h2 = ( t1, t2, …, td, f1, …, fn ) h2 把表和被查值拼在一起；接下来要证的是 h1 与 h2 的多重集相等

于是要证的变成：h1 和 h2 作为多重集相等， 外加「h1 是有序的」。前者用累乘，后者用相邻比较约束。

05累乘多项式：把「连乘」变成「可验证的一列」

直接让验证者算 Π(ai+α) 要 O(n) 次乘法。做法是把累乘结果做成一个多项式 Z， 在每一行的取值就是「到这一行为止的连乘」。

在单位根 gi 上定义：

Z(g0) = 1,    Z(gi+1) = Z(gi) · ( 1 + α h1(gi) ) / ( 1 + α h2(gi) ) 逐行递推：每行乘上「分子的一项」再除以「分母的一项」

最后检查首尾闭合：

Z(gn+d) = Z(g0) = 1 如果 h1 和 h2 的多重集相等，所有分子分母两两抵消，累乘回到 1

为什么这个检查足够

  • 如果所有值都配对成功，乘积逐项抵消，终点必然回到 1。
  • 如果有一个值对不上（比如 f 里混进了表外的 y）， 那么分子里会多出一个 (1+αy) 而分母里没有，终点变成 (1+αy) 的某个幂，不等于 1。
  • 攻击者想凑出「不等于 1 但看起来等于 1」的结果，需要猜中 α —— 概率 1/p。
✓
代价对比

原本 n 条范围检查约束，现在变成 一条累乘递推约束（外加排序约束）。 n 越大，省得越多。这就是为什么 zkEVM 里「查表」几乎替代了所有位运算。

06两个能手算的例子

排序交错的细节因实现而异（Plookup、Halo2、LogUp 各不相同）， 但底层那个「指纹」工具是一致的。手算一遍它，比记实现细节有用得多。

例一：配对成功

被查值 f = (2, 3, 2)，表 t = (1, 2, 3)，取 α = 5（真实中 α 是随机大数）。

把 f 和 t 的每一项都算成 (值 + α)：

f → ( 2+5, 3+5, 2+5 ) = ( 7, 8, 7 )
t → ( 1+5, 2+5, 3+5 ) = ( 6, 7, 8 )

注意两边长度不同（3 和 3），但语义上 f 是 t 的子多重集： f 用了两次 2、一次 3，所以 t 里的 2 需要被「用掉」两次。 这就是为什么直接比连乘会失败 —— 必须先把重数对齐。

i
对齐重数：t 需要按需扩展

Plookup 的做法是把 t 扩展成「足够长」的序列，让每个表项出现的次数不少于被查次数。 实现上通过 s = sort(f ∪ t) 完成：s 天然带着正确的重数。 这一步是纯组合操作，不涉及密码学。

例二：混入表外值，指纹必然对不上

把 f 改成 (2, 3, 9)，其中 9 不在表里。取 α = 5：

f → ( 7, 8, 14 )   ← 14 = 9+5，这一项在表里找不到对应
t → ( 6, 7, 8 )

无论怎么排序、怎么配对，14 这个因子都会留在分子里无法被约掉。 最终累乘的结果不等于 1，验证失败。

Zfinal = Π(分子) / Π(分母) = ( 7 · 8 · 14 ) / ( 6 · 7 · 8 ) = 14/6 ≠ 1 实际操作中分子分母是同一组序列的交错排列，这里为直观做了简化

这就是查找论证的全部威力：一个不在表里的值，会让一个连乘结果偏离 1。 验证者只要检查这个结果，就知道有没有人查了不存在的表项。

累乘是怎么走的

真实协议不会真的把所有项乘起来（那是 O(n) 的），而是把「到第 i 行为止的乘积」做成多项式 Z 的取值。 每一行只做一次「乘一个、除一个」：

Zi+1 = Zi · ( 1 + α h1,i ) / ( 1 + α h2,i ) 一行一次乘除，n+d 行之后检查 Z 是否回到 1

由于 Z 是一个多项式在单位根上的取值，它可以被承诺、被打开、被验证 —— 于是「连乘」这件事本身也进入了 SNARK 的证明范围。

07LogUp 与 cq：更省的新一代

Plookup 的累乘要做大量域乘法，而且每个查找都要一个单独的 Z 多项式。 后来的方案换了个思路：用倒数之和代替连乘。

LogUp 的核心恒等式

Σi 1 / ( α − fi ) = Σj mj / ( α − tj ) mj 是表项 tj 被查询的次数（多重度）

如果每个 fi 都来自表，那么左边的每一项都能在右边找到对应的项， 两边作为有理函数恒等。反之，如果混进了表外的值 y，左边会多出 1/(α−y) 这一项，无法被右边抵消。

这个形式的好处：不需要排序（排序是 Plookup 里最贵的部分）， 而且多个查找可以批量合并成一个。

cq 的做法

cq（Customizable Constraint Systems 里的 lookup 变体）进一步把「表」也变成可承诺的对象， 支持运行时构造表、甚至表与表之间互相查找。zkEVM 里的「opcode 表 → 状态表 → 内存表」 这种链式查找，用 cq 表达最自然。

方案核心工具特点
Plookup排序 + 累乘第一个实用方案，证明大，需要排序网络
Halo2 lookupZ 多项式 + 重排工程成熟，zkEVM 广泛使用
LogUp倒数和无需排序，可批量，证明更小
cq列式查找表可自定义，适合复杂状态机

08小结与常见误区

你应该带走的

  • 查找论证解决的是「非算术操作太贵」，把约束换成查表。
  • 核心工具是多重集的随机指纹：Π(ai+α) 或 Σ1/(α−ai)。
  • 「包含」通过补一个排序序列 s 化归成「相等」。
  • 累乘多项式 Z 把 O(n) 的连乘变成一列可验证的递推。
  • LogUp 用倒数和替代连乘，省掉了排序这个最贵的步骤。
✕「查表就是免费的，表越大越好。」
✓
表本身要作为公开输入参与承诺，表越大，验证者的公开输入越长、配对次数越多。 65536 项的表在链上验证成本已经不低。表的大小要和查询次数匹配。
✕「查找论证能替代所有范围检查。」
✓
它替代的是「离散的、可枚举的」检查。如果范围是 [0, 264)， 表就有 264 项，不可能物化。实际做法是拆成多个小表（比如 16 位一段）分几次查。
✕「查表就是排序后比前 d 项，很简单。」
✓
这个简化在有重复值时会给出错误结论。真正的判定是多重集语义下的 交错一致性，外加 s 的有序性约束。看到把 Plookup 讲成「比前 d 项」的材料， 基本可以判断它省略了关键细节。
✕「查找论证只能处理整数表。」
✓
表里的元素是域元素，可以是整数、也可以是打包后的结构化数据 （比如把「地址 + 余额 + nonce」哈希成一个值放进表）。 zkEVM 正是用这种方式把「状态转移」编码成查表，而不是逐字段比较。
