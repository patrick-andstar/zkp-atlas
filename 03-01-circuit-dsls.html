电路 DSL：不能用 Rust 直接写电路

你熟悉的语言都在「描述计算过程」，而电路需要的是「描述约束关系」。 这两件事的差别，决定了为什么会有 Circom、Noir、Cairo 这些专门的语言 —— 以及为什么写电路比写普通程序容易出安全漏洞。

动手第一站 ≈ 15 min 难度 3 / 5 前置：算术化 产出：可编译的电路

01为什么不能用普通语言写

在 Rust 里写 let y = x * x;，编译器生成的是「乘一次，存起来」。 在电路里，这行代码的含义完全不同：它要么是「算出 y 的值」，要么是「约束 y 等于 x²」，或者两者都是。

这三种语义在普通语言里没有区分，但在电路里必须显式表达：

语义Circom 写法含义
只赋值y <-- x * x;算出 y，但不约束它等于 x²
只约束y === x * x;声明等式，但不计算 y（y 必须已在别处赋值）
两者都做y <== x * x;赋值 + 约束，最常用

为什么需要「只赋值」？因为有些计算在电路里很难直接表达（比如开方、位分解）， 你需要先用普通计算算出结果，再单独加约束验证它。

!
这就是 90% 电路漏洞的来源

用了 <-- 却忘了加 ===，等于告诉证明者「这个变量你随便填」。 编译能过、证明能生成、链上能验证 —— 但业务规则已经失效了。

02四个主流选择，定位完全不同

语言背后是谁抽象层次典型用户
Circomiden3 低层。手写约束，直接对应 R1CS Groth16 项目、Tornado Cash、Semaphore
NoirAztec 中层。Rust 风格，编译器生成 ACIR 通用应用、想快速上手的人
CairoStarkWare 高层。写起来像普通程序，编译成 AIR StarkNet 生态
Halo2Zcash / PSE 最低层。Rust API，直接操作 PLONKish 表格 zkEVM、需要极致优化的团队

注意抽象层次的差别：越高层越好写，但越难控制约束数量。 Cairo 写起来最舒服，但生成的 AIR 约束可能比你手写的多几倍； Halo2 写起来最痛苦，但每一行表格都在你掌控中。

03Circom 实战：写一个范围检查

目标：约束 in 是一个 8 位无符号数（0 到 255）。 这在电路里必须拆成比特，因为域元素没有「位宽」概念。 

pragma circom 2.0.0;

template RangeCheck8() {
    signal input in;
    signal output ok;

    signal bits[8];
    var sum = 0;

    for (var i = 0; i < 8; i++) {
        // 只赋值：把 in 的第 i 位取出来
        bits[i] <-- (in >> i) & 1;

        // 关键约束：每个 bit 必须是 0 或 1
        bits[i] * (bits[i] - 1) === 0;

        sum += bits[i] * (1 << i);
    }

    // 关键约束：拼回去必须等于原值
    sum === in;

    ok <== 1;
}

component main = RangeCheck8();

这段代码只有 9 条约束（8 条比特约束 + 1 条求和约束）。逐条看：

语句作用约束数
bits[i] <-- ...用普通计算取出第 i 位。这是「赋值」，不受约束0
bits[i]*(bits[i]-1) === 0强制比特只能是 0 或 11
sum === in拼回去必须等于输入1
!
如果删掉 bits[i]*(bits[i]-1) === 0 会怎样

证明者可以令 bits[0] = 300、其余为 0，只要 sum 恰好等于 in。 更糟的是，他可以让 bits 取任意值来「凑」出想要的 sum —— 范围检查彻底失效，而电路依然能生成合法证明。

04赋值与约束：必须形成肌肉记忆

x <-- expr   只赋值。证明者可以填任意值，只要后续约束满足
x === expr   只约束。不计算，x 必须已在别处有值
x <== expr   两者都做。最安全，优先用它

什么时候必须用 <--

当表达式不是低次多项式时。比如：

  • 位分解：(in >> i) & 1 —— 位运算是非算术的
  • 比较：a < b ? 1 : 0 —— 需要借用比较逻辑
  • 除法：a / b —— 域里没有除法，要乘逆元

这些都必须「先算后证」：用 <-- 算出来，再用 === 加一组约束把它钉死。

一个反面教材

// 错误：只赋值，没有约束
signal inv;
inv <-- 1 / in;

// 正确：加一条约束验证它
inv * in === 1;

第二种写法还有额外好处：如果 in = 0，约束 inv * 0 = 1 无法满足， 证明直接失败 —— 这顺便防住了「除以零」。

05工具链：从 .circom 到链上验证

1

编译

circom range.circom --r1cs --wasm --sym

产出三个文件：.r1cs（约束系统）、.wasm（见证生成器）、.sym（调试符号表）。

2

可信设置

snarkjs groth16 setup range.r1cs pot12_final.ptau range_0.zkey

用已有的 Powers of Tau 文件 + 你的电路，生成电路专用密钥。

3

生成证明

node generate_witness.js range.wasm input.json witness.wtns
snarkjs groth16 prove range_0.zkey witness.wtns proof.json public.json

input.json 里放公开和私密输入，输出证明和公开信号。

4

导出验证合约

snarkjs zkey export solidityverifier range_0.zkey Verifier.sol

得到一个 Solidity 合约，把 proof.json 的三个点传进去调用 verifyProof。

i
一个容易踩的坑

.zkey 是电路专用的。改一行 Circom 代码，就必须重新生成 .zkey， 但 .ptau 可以复用（它是通用的幂次，与电路无关）。 搞混这两个文件的作用，会浪费很多时间。

06怎么选：按「你在做什么」而不是「哪个更先进」

你的情况建议理由
第一次写电路，想快速看到结果Noir语法接近 Rust，工具链一键走通，不用手工管仪式
要上以太坊，gas 敏感Circom + Groth16证明最小（128 B），社区教程最多
做 zkEVM / 需要查找表Halo2 或 Circom + PLONKPLONKish 的表达力不可替代
做 StarkNet 应用Cairo原生集成，不用自己搭证明服务
要极致性能、愿意读源码Halo2 / Plonky3每一层都可调，但没有「开箱即用」
✓
给第一次动手的建议

先用 Noir 写一个「证明我知道 x 使 x² = 9」的小电路，跑通全流程（编译 → 证明 → 验证）。 这一步会暴露你对「公开/私密输入」的理解偏差 —— 而这比读十篇文章有用。

07小结与常见误区

你应该带走的

  • 电路语言的核心区分是「赋值」与「约束」，普通语言没有这个区分。
  • Circom 的 <== 同时做两件事，<-- 只赋值 —— 后者必须配 ===。
  • 位运算、比较、除法都必须「先算后证」。
  • 四个 DSL 的差别是抽象层次：越高层越好写，越难控制约束数。
  • .ptau 通用可复用，.zkey 电路专用必须重生成。
✕「会用 Rust 就会写电路。」
✓
语法像，思维完全不同。普通程序是「怎么算」，电路是「算什么必须成立」。 写电路时你更像在写测试断言，而不是在写实现。
✕「编译器会帮我检查约束是否完整。」
✓
不会。约束缺失在语法上完全合法，编译器没有任何理由报错。 这是语义层面的漏洞，只能靠审计和形式化验证发现。
✕「约束越多越安全。」
✓
约束多只让证明变慢。安全性取决于该有的约束是否都有。 一条多余的约束不增加安全，只增加成本。
✕「Circom 编译出的 wasm 可以直接上链。」
✓
wasm 只是本地生成见证用的。上链的是 proof（三个群元素）和验证合约。 把 wasm 和 proof 搞混，是初学者最常见的部署错误。
