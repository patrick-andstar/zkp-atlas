折叠方案：不验证，先把两个证明折起来

递归 SNARK 的每一步，都要在电路里验证前一步的证明 —— 而「验证一个 SNARK」本身是几万条约束。 Nova 换了个思路：先不验证，把新旧两个实例折叠成一个，最后只证明一次。

≈ 16 min 难度 5 / 5 前置：R1CS · 承诺 后续：IVC · 增量计算

01这个模块要解决的问题

有一类计算是「一步一步往前推」的：虚拟机执行 100 万条指令、区块链处理 100 万个区块、神经网络跑 100 层。 你想证明「这 100 万步全都正确」，但不想为每一步生成一个证明。

递归 SNARK 的做法是：第 i 步生成一个证明 πi， 证明「πi−1 有效，且第 i 步计算正确」。 问题在于 —— 验证 πi−1 这件事本身要被写进电路， 而它包含配对运算、哈希、群加法，动辄几万条约束。

做法每步成本问题
每步生成一个 SNARK证明生成（秒级）100 万步 = 100 万个证明，无法聚合
递归 SNARK证明生成 + 电路内验证电路内验证占 90% 以上开销
折叠方案一次群运算（微秒级）只有最后一步需要生成真正的 SNARK

差距是数量级的：递归 SNARK 每步要几十毫秒，折叠方案每步只要几十微秒。

02直觉：把两张试卷合成一张

你有两张待批改的试卷，每张都有 100 道题。逐个批改要 200 次判断。 但如果两张卷子的题目结构完全一样，你可以把「第 1 题 + 第 1 题」「第 2 题 + 第 2 题」…… 合成一张新卷子 —— 批改这张新卷子，等于同时批改了原来两张。

折叠方案就是这个思路：两个结构相同的约束系统实例，可以线性组合成一个新实例， 而新实例的可满足性蕴含原来两个都可满足。

( 实例1 , 实例2 )  ⟶  实例3 实例 3 的规模与实例 1 相同 —— 不是「合并成两倍大」，而是「压回原来大小」

关键点：折叠不产生证明，只产生一个新实例。 所以它极快，但也不提供任何零知识性或可靠性 —— 那些要等到最后一步生成 SNARK 时才获得。

i
为什么可以「不验证就折叠」

因为折叠是代数恒等变形：如果两个输入都满足约束，输出必然满足； 如果输出满足，也不能推出输入都满足（这是单向的）。 所以折叠本身不安全 —— 它的作用是「累积待验证的工作」，最后一次性交给 SNARK。

03Relaxed R1CS：必须先把约束放松一点

标准的 R1CS 是 (Az)∘(Bz) = Cz。这个形式对线性组合不封闭 —— 两个满足它的实例加起来，一般不满足。所以 Nova 引入了一个「放松版」。

( A·z ) ∘ ( B·z ) = u · ( C·z ) + E Relaxed R1CS：多了一个标量 u 和一个误差向量 E
符号含义标准 R1CS 里对应什么
u标量，称为「松弛因子」恒等于 1
E误差向量，长度等于约束条数恒等于零向量
z见证向量相同

当 u = 1 且 E = 0 时，它就退化成标准 R1CS。 所以「放松」的意思是：允许一点点「不满足」，把这点残差记在 E 里。

为什么要放松？因为两个实例线性组合后，交叉项会冒出 (Az₁)∘(Bz₂) 这类东西， 无法再保持等式严格成立。把残差吸收进 E，就重新封闭了。

04折叠公式：一个随机数搞定

给定两个 relaxed 实例 (u₁, E₁, z₁) 和 (u₂, E₂, z₂)，取随机挑战 r：

u = u1 + r · u2
z = z1 + r · z2
E = E1 + r·( Az1∘Bz2 + Az2∘Bz1 − u1Cz2 − u2Cz1 ) + r2·E2 折叠后的新实例 (u, E, z)，规模与原来单个实例相同

这个公式看起来复杂，但来源很朴素：把两个等式分别乘以 1 和 r，再相加，然后把所有「多出来的项」塞进 E。

推导：三步

1

各自乘以系数

第一个实例乘 1，第二个乘 r，得到两个等式：

(Az₁)∘(Bz₁) = u₁(Cz₁) + E₁
r·[(Az₂)∘(Bz₂)] = r·[u₂(Cz₂) + E₂]
2

相加，并注意交叉项

左边相加时，(Az₁+ rAz₂)∘(Bz₁+ rBz₂) 展开会出现四个部分：

(Az₁)∘(Bz₁) + r[(Az₁)∘(Bz₂)+(Az₂)∘(Bz₁)] + r²(Az₂)∘(Bz₂) 中间那两项就是交叉项，标准 R1CS 里没有它们的位置
3

把交叉项和残差都归入 E

定义新的 u = u₁ + r·u₂、z = z₁ + r·z₂， 再把所有不能写成 u·(Cz) 的项全部移进 E。 整理后就得到上面的公式。

✓
为什么这一步几乎免费

折叠只需要几次向量加法和两次内积，全是 O(n) 的域运算， 没有配对、没有 FFT、没有证明生成。这就是微秒级的来源。

05IVC：增量可验证计算怎么用它

IVC（Incrementally Verifiable Computation）要证的是：「函数 F 迭代了 n 次，从 z₀ 得到 zₙ」。 用折叠方案的流程如下。

1

初始

从 z₀ 开始，构造第一个 relaxed 实例，记录「当前状态是 z₀」。

2

每一步：折叠，不证明

计算 zi+1 = F(zi)，把「这一步的计算正确」编码成一个新实例， 然后折叠进累加器。全程只做群运算和域运算。

3

最后一步：生成一个 SNARK

经过 n 次折叠，你手上有一个「累积了 n 步」的实例。 对它生成一个 SNARK，证明「这个累加器是可满足的」。

4

验证

验证者只验证这一个 SNARK，就相信了全部 n 步。证明大小与 n 无关。

i
代价转移到了哪里

折叠把「每步验证」的成本，转移成了「最后一次性证明」。 但如果 n 非常大（比如 109），最后那个 SNARK 的电路规模也会很大。 实际系统会把折叠和递归组合使用：每折 1000 步，生成一个 SNARK，再把这个 SNARK 折进上一层。

06和递归 SNARK 的区别

维度递归 SNARK折叠方案（Nova）
每步做什么生成证明 + 电路内验证前一个证明一次线性组合（折叠）
每步成本几十毫秒几十微秒
证明数量每步一个全程只有一个（最后生成）
需要配对是（如果底层是 pairing-based）否
零知识每步都有只有最后一步有
适用场景需要中间状态可验证只需最终结果正确

一句话总结：递归是「每步都结账」，折叠是「先记账，最后一起结」。 前者适合需要中间证明的场景（比如跨链桥要随时验证某段历史）， 后者适合「我只关心最终结果」的长计算（比如训练验证、虚拟机执行）。

后续发展

Nova 之后出现了 SuperNova（支持不同电路）、HyperNova（支持自定义约束系统）、 Protostar（支持高次约束）、ProtoGalaxy（多实例折叠）。 共同思路都是「把验证推迟，把折叠做便宜」。

07小结与常见误区

你应该带走的

  • 折叠 = 把两个同构实例线性组合成一个，规模不变。
  • 必须先把 R1CS 放松成 (Az)∘(Bz) = u(Cz) + E，否则对线性组合不封闭。
  • 折叠本身不提供安全性，只是累积工作，最后靠一个 SNARK 收口。
  • 每步成本从毫秒级降到微秒级，因为只做域运算。
  • 折叠与递归可以组合：分级折叠，避免最后那个 SNARK 过大。
✕「折叠就是一种更快的 SNARK。」
✓
它不是证明系统，是证明的预处理。折叠本身不产生任何可验证的证明， 也不能单独使用。必须配一个底层 SNARK 才有意义。
✕「折叠后如果可满足，说明每一步都正确。」
✓
方向是反的：每步正确 ⟹ 折叠后可满足。 反过来不成立 —— 一个可满足的折叠实例，可能对应若干组不同的原始实例。 安全性来自最后 SNARK 对「折叠关系本身」的证明，不是折叠的代数性质。
✕「有了折叠就不需要递归了。」
✓
两者解决不同问题。折叠省的是中间验证，递归省的是证明体积。 大规模系统通常两者都用：折叠处理步数，递归处理层级。
✕「折叠后的实例可以单独拿去验证。」
✓
不能。折叠后的 (u, E, z) 只是一个待证明的承诺， 必须再生成一个 SNARK 才具有可验证性。把它直接发给验证者，对方无法判断它是否来自合法计算。
