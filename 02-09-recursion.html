递归组合：让证明去验证另一个证明

一个 SNARK 证明了「这段计算是对的」。但如果计算本身在增长呢？ 区块链每秒产生新块，虚拟机每秒执行新指令。递归让最新那个证明里， 包含着「之前所有历史都正确」的证据。

进阶模块 ≈ 16 min 难度 5 / 5 前置：证明系统 · 折叠方案 后续：工程层的聚合

01这个模块要解决的问题

假设你要证明「这条链从创世块到现在的每一个区块都合法」。 最直接的办法是生成一个巨大的电路，把全部历史塞进去 —— 但历史会不断变长，电路规模没有上限。

递归的思路是：证明的验证过程本身，也可以被写进电路。 于是你可以构造这样一条链：

πi = 证明( 「πi−1 有效」 ∧ 「第 i 步计算正确」 ) 每个证明都在说：前 i−1 步全对，加上这一步也对

这样证明的大小是常数，但覆盖的计算量可以无限增长。 验证者只验最后一个 πn，就相信了全部 n 步。

i
这和「折叠」的区别

折叠（上一模块）是推迟验证：先攒着，最后一次性证明。 递归是立即自证：每一步都产出一个完整证明，且这个证明包含对前一步的验证。 递归的证明可以单独拿出来用，折叠的不行。

02直觉：俄罗斯套娃，但每层都一样大

普通的套娃越往里越小，递归 SNARK 反过来：最外层和里面那层一样大。

想象你有一台「证明复印机」。你把一份证明塞进去，它输出一份新的证明， 内容变成「旧证明有效 + 我又做了一步」。输出的大小和输入完全一样。

于是你可以无限地喂进去：π₀ → π₁ → π₂ → … → πn。 最后拿出来的 πn 只有几百字节，但它背后的计算量是 n 步。

| πi | = O(1)   而   它能覆盖的计算量 = i 步 这就是「简洁性」在时间维度上的延伸

03IVC：把「套娃」写成定义

IVC（Incrementally Verifiable Computation）是递归的形式化模型。 它描述的是一类计算：从初始状态出发，反复应用同一个函数。

z0  →  z1 = F(z0)  →  z2 = F(z1)  →  ⋯  →  zn = F(zn−1) F 是状态转移函数；z 是完整状态（比如虚拟机的全部寄存器 + 内存根）

IVC 要求证明者输出 (zn, πn)，使得：

  • 正确性：πn 证明「存在一条从 z₀ 到 zn 的合法路径」；
  • 简洁性：πn 的大小与 n 无关；
  • 增量性：生成 πi 只需要 πi−1 和 zi，不需要重算历史。

第三条是「增量」的含义：生成新证明的成本是常数，不管你已经跑了多少步。 没有这一条，递归就没有工程价值。

三要素为什么缺一不可

缺掉哪一条会发生什么
缺正确性 证明不再有意义 —— 验证者接受了它，但背后的计算可能是错的。整个系统退化成「一个很贵的签名」
缺简洁性 证明随步数增长。跑一百万步就得到一百万个群元素，和「把历史全发过去」没有区别
缺增量性 每一步都要从头重算，复杂度 O(n²)。理论上还能工作，工程上完全不可用

这三条不是「最好都有」，而是定义的一部分。 很多论文里的「递归证明」只满足前两条，第三步靠工程手段（缓存中间状态）补 —— 这种实现通常跑不了长链。

04递归电路里到底装了什么

这是最容易含糊的地方。说「在电路里验证一个 SNARK」，具体是哪些约束？

1

验证密钥的哈希

电路里要硬编码 vk 的摘要，确保「被验证的证明用的是同一个电路」。 否则攻击者可以换一个对自己有利的 vk。

2

公开输入的绑定

前一步的公开输入（比如旧状态根）必须等于当前步的某个输入。这一条把「链」接起来。

3

配对 / 哈希的验证逻辑

如果底层是 Groth16，电路里要实现椭圆曲线配对 —— 这是几万条约束的大头。 如果底层是 FRI-based，电路里要做哈希和 Merkle 路径检查，相对便宜但也不小。

4

本步计算 F 的约束

真正「干活」的部分。讽刺的是，在很多 IVC 系统里，验证前一个证明的开销 远大于本步计算本身 —— 这就是折叠方案出现的动机。

底层方案电路内验证的主要成本量级
Groth16（配对）椭圆曲线配对运算~ 数万约束
FRI / STARK哈希 + Merkle 路径~ 数千约束
IPA（Halo2）群运算 + 内积~ 数千约束

验证密钥该不该进电路

答案看起来很明显（当然要），但这里有三种做法，安全性差别很大：

做法安全性问题
硬编码完整 vk 最高 电路规模大，每次改 vk 要重编电路
硬编码 vk 的哈希 高 电路里要多做一次哈希验证，额外几千条约束
把 vk 当公开输入 危险 证明者可以换一个对自己有利的 vk —— 除非外层还有约束把它钉住

第三种做法在「通用递归」场景下是必要的（比如 Nova 要支持任意电路）， 但必须配合「vk 由前一层证明承诺」的机制。单独把 vk 当公开输入，等于没有约束。

05循环曲线问题：一个必须绕过的坑

递归有一个看起来很尴尬的技术障碍：你要在曲线 A 的电路里，验证曲线 A 上的运算。 但电路是用标量域定义的，而群运算定义在基域上 —— 两者大小不匹配。

具体说：BN254 的基域是 254 位，标量域也是 254 位，但两者是不同的素数。 电路的约束在标量域上，而验证配对需要基域元素。直接做会导致「域元素放不进电路」。

两种解法

方案做法代表
循环曲线
cycles of curves		 选两条曲线，A 的基域等于 B 的标量域，反之亦然。在 A 上证明，在 B 上验证，交替进行。 Pasta 曲线（Pallas / Vesta），Halo2 使用
非原生域运算
non-native arithmetic		 在电路里用多个小域元素模拟大域元素，代价是约束数翻几倍。 多数早期 Groth16 递归实现

循环曲线的优雅之处：两边的域大小天然对齐，不需要模拟，约束数大幅下降。 代价是要维护两套曲线和两套电路，工程复杂度翻倍。

i
为什么这条曲线叫「Pasta」

Pallas 和 Vesta 是希腊神话里的两个名字，合起来谐音 pasta（意大利面）。 Zcash 团队起的名字 —— 密码学圈的命名品味一直很稳定。

06聚合 vs 递归：目标不同

这两个词经常被混用，但它们解决的不是同一个问题。

维度递归（recursion）聚合（aggregation）
输入一个证明 + 一步新计算n 个独立的证明
输出一个覆盖更多步骤的证明一个「这 n 个都有效」的证明
关系时间上的串联空间上的并联
典型用途区块链历史、虚拟机执行多个用户的交易批量验证
代表Nova、Halo2 递归、zkSyncSnarkPack、Groth16 聚合

一句话：递归是「把历史压成一个」，聚合是「把一批压成一个」。 实际系统经常两者都用：先把一批交易聚合，再把聚合结果递归进历史。

聚合的三种形态，成本差很多

形态做法限制
配对聚合 利用双线性把 n 个验证等式乘起来，只算一次多配对 只能聚合同电路、同 vk 的证明
递归聚合 把 n 个证明的验证过程写进电路，生成一个新证明 电路内验证成本高（几万约束）
证明聚合树 两两合并成二叉树，逐层向上 深度 log n，需要多轮递归

选型的判断标准是「这 n 个证明是不是同一个电路产生的」： 是 → 配对聚合，几乎免费；否 → 递归聚合，贵但通用。

07小结与常见误区

你应该带走的

  • 递归 = 在电路里验证前一个证明，从而让证明大小与计算量解耦。
  • IVC 的三要素：正确性、简洁性、增量性（成本不随步数增长）。
  • 电路里验证的开销往往远大于本步计算，这是折叠方案的动机。
  • 循环曲线（Pallas/Vesta）解决「域大小不匹配」，代价是双倍工程复杂度。
  • 递归是串联历史，聚合是并联批次，不要混用。
✕「递归就是证明套证明，很简单的想法。」
✓
想法简单，实现极难。要在电路里重写整套验证逻辑（配对、哈希、群运算）， 还要处理域不匹配、证明系统自举、以及性能优化。这是 ZKP 工程里最硬的一块。
✕「递归之后证明会越来越小。」
✓
不会变小，而是保持不变。递归的意义是「不增长」， 不是「压缩」。想要更小，需要换证明系统或做包装（比如 STARK 包成 Groth16）。
✕「有了折叠就不需要递归了。」
✓
折叠不产生可独立验证的证明。如果你需要「随时拿出某一步的证明给别人看」， 必须用递归。折叠适合「只关心最终结果」的场景。
✕「递归电路的规模是固定的，所以成本是常数。」
✓
规模固定不等于成本低。一个递归电路可能包含几万条约束验证逻辑， 每步都要跑一遍。「常数」是相对于步数而言，绝对值可能很大。
