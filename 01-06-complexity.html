复杂性理论：证明为什么能被压缩

「证明」在数学里是一串推理，在计算机科学里是一个可被高效检查的字符串。 把「检查」放松成「随机抽查」，能换来什么？答案是：证明可以短到与计算量无关。

≈ 14 min 难度 3 / 5 前置：无（概念性） 被用于：理解 SNARK 的理论边界

01这个模块要解决什么问题

日常语境里，证明是一段让人信服的论证。但在计算理论里，它必须被定义成 一个可以被机器检查的对象，否则没法讨论「多短」「多快」。

最朴素的定义是：

对语言 L，证明系统是一对算法 ( P, V )，满足：
完备性：x ∈ L ⟹ V(x, P(x)) = 1
可靠性：x ∉ L ⟹ 对任意 P*, V(x, P*(x)) = 0 V 是多项式时间的验证者；P 可以任意强（甚至无限算力）

这个定义里，V 要读完整个证明。证明长度 = 验证时间。 想让它短，就得改定义。

接下来四步，每一步都在放松一个约束，最终得到 SNARK 的理论原型。

02第一步：NP —— 允许「见证」

L ∈ NP  ⟺  存在多项式时间验证器 V，使得
x ∈ L  ⟺  ∃w, |w| ≤ poly(|x|),   V(x, w) = 1 w 叫「见证」（witness），就是那个「答案」

例子：图的三染色。x 是一张图，w 是每个顶点的一个颜色。 验证者检查「每条边两端颜色不同」—— 这是多项式时间的。

NP 的关键：证明（见证）可以比计算过程短得多。 但要检查它，仍然要读完整个 w，所以验证时间是 O(|w|)。

i
SNARK 要证的就是 NP 命题

「我知道一个 w 使 R(x,w)=1」—— 这就是 NP 的定义。 所以 SNARK 的表达力上限就是 NP，不能说「证明任意数学猜想」。

03第二步：IP —— 允许「交互」

如果让验证者和证明者来回对话，验证者能验证的问题会变多吗？ 直觉上应该不会 —— 对话只是把信息分批给。 但 1992 年 Shamir 证明了：会，而且多得多。

IP = PSPACE 交互式证明能验证的问题，恰好等于「多项式空间可解」的问题

PSPACE 被认为远大于 NP（比如「这个棋局先手是否必胜」在 PSPACE 里，但不确定是否在 NP 里）。 所以交互确实增强了验证能力。

为什么交互有用

因为验证者可以随机提问，而证明者事先不知道问题。 如果证明者在撒谎，他很难在所有可能的提问下都自圆其说。

这就是「零知识」的技术基础：Schnorr 协议里那个随机挑战 c， 就是验证者的提问权。没有它，证明者可以随便编。

04第三步：PCP —— 只查几个位置

1992 年同一年，另一个结果震动了整个领域：PCP 定理。 它说：任何 NP 证明都可以改写成一种特殊形式，使得验证者只读常数个位置就能判断真假。

PCP 定理：  NP = PCP[ O(log n) , O(1) ] 用 O(log n) 个随机比特，查询 O(1) 个位置，就能以高概率判断 x ∈ L
参数含义
O(log n)随机比特数。决定「有多少种可能的抽查模式」
O(1)查询位置数。常数，与证明长度无关
可靠性如果命题为假，任何证明都会在至少一半的抽查模式下暴露

这个定理的意义：「验证」可以比「阅读」便宜得多。 你不需要读完整个证明，只需要随机戳几个位置。

!
但 PCP 定理不是 SNARK

PCP 是存在性结果：证明那个「改写后的证明」存在，但没给高效构造方法。 从 PCP 到实用 SNARK，中间隔了二十年的工程密码学（KZG、FRI、Groth16）。 理论上很美，直接用会很慢。

证明长度和查询次数是一对矛盾

PCP 定理说「查询常数个位置」，但没说这个常数是多少，也没说证明有多长。 实际上，要达到可接受的可靠性，证明长度往往是原始计算的多项式倍 （有些构造是 n³ 甚至更高）。

参数理论构造实用系统
证明长度poly(n)，常数巨大O(n) 或更小
查询次数常数（但可能上百）log n 或常数
验证时间常数，但常数项大毫秒级
能否直接实现否（构造不高效）是

这就是为什么 SNARK 不是「实现 PCP」，而是绕开 PCP，用 IOP + 承诺： 把「读一个超长字符串的某几个位置」换成「打开一个承诺的某几个位置」， 长度从 poly(n) 降到 O(n) 的承诺，再压到常数大小的证明。

05第四步：IOP —— 证明变成一个「预言机」

PCP 里证明是一串固定的比特，验证者去查它的某些位置。 但如果证明本身可以是一个函数（你给我输入，我返回值），表达能力会更强。

IOP（Interactive Oracle Proof）：证明是一个预言机 π，
验证者可以自适应地查询 π(i)，并根据结果决定下一个问题 PCP 是「非自适应」的特例；IOP 允许「问一步、看一步」

STARK 本质上是 IOP + 哈希承诺： 多项式就是那个预言机，Merkle 树就是承诺，FRI 就是查询协议。

从「预言机」到「Merkle 树」：中间差了什么

IOP 里「查询 π(i)」是一个抽象动作，数学上假设它免费且可靠。 现实中没有免费的查询，必须用承诺把它实现出来：

IOP 里的抽象现实中的实现代价
证明 π 是一个函数把求值表建成 Merkle 树O(n) 哈希
查询 π(i)Merkle 路径 + 叶子值O(log n) 个哈希
验证者自适应提问Fiat–Shamir 把问题变成哈希一次哈希

这三步替换之后，IOP 从一个「信息论对象」变成了「可以在互联网上传输的协议」。 STARK 的全部工程复杂度，几乎都在这三层映射里。

模型证明形式验证方式典型实现
NP字符串 w读完整个 w—
IP交互对话多轮问答Schnorr、Groth16（交互版）
PCP长字符串随机查常数个位置理论构造，无实用
IOP预言机（函数）自适应查询 + 承诺STARK、FRI

06这些理论和 SNARK 的对应关系

把 SNARK 的每个零件映射回理论模型，会看得更清楚：

SNARK 里的东西理论对应
「我知道 w 使 R(x,w)=1」NP 命题
随机挑战（Fiat–Shamir 的 c）IP 里验证者的随机提问
多项式承诺 + 打开PCP/IOP 里的「查询某个位置」
FRI 的折叠与抽查低度测试 + PCP 的随机查询
简洁性（常数大小）PCP 定理的 O(1) 查询
可靠性（1/p 量级）PCP 的 soundness error

一句话：SNARK 是 PCP/IOP 的密码学工程实现。 理论告诉你「可以只查几个点」，工程告诉你「怎么让那几个点不可伪造」。

07理论上限：有些事做不到

复杂性理论不只给希望，也给限制。三条值得记住：

  • SNARK 只能证 NP。想证「这个程序会停机」，如果问题本身不可判定，就没有电路能表达它。
  • 非常数大小的证明不可能覆盖任意计算。简洁性是有代价的：要么需要可信设置， 要么依赖强假设，要么证明变大。
  • 零知识不等于「什么信息都没有」。它只保证「不泄露超出命题为真的信息」—— 公开输入本身仍然是公开的。
i
一个常被问的问题

「能不能用 SNARK 证明 P ≠ NP？」不能。 因为 P ≠ NP 不是一个「存在短见证」的命题 —— 它是对所有算法的断言，不是 NP 的形式。 这也说明 SNARK 的边界很清晰：它处理的是「有具体解的验证问题」。

08小结与常见误区

你应该带走的

  • NP = 有短见证、可高效验证的命题。SNARK 的适用范围就是 NP。
  • IP = PSPACE：交互能显著增强验证能力。
  • PCP 定理：任何 NP 证明都能改写成「只查常数个位置」的形式。
  • IOP 把证明变成预言机，是 STARK 的理论基础。
  • SNARK = PCP/IOP + 密码学承诺，把理论构造变成可实现的协议。
✕「SNARK 可以证明任何数学定理。」
✓
只能证明NP 命题，而且要先把命题写成电路。 「黎曼猜想」这种对无穷多对象的断言，不在 NP 里。
✕「PCP 定理可以直接拿来写代码。」
✓
PCP 的证明长度是多项式级但常数巨大，构造也不高效。 实用系统都用 IOP + 承诺绕开它。理论保证存在，工程负责让它跑得动。
✕「交互式证明比非交互式更强。」
✓
表达力上 IP ⊇ NP，但非交互式（NIZK）在工程上不可替代： 可上链、可转发、可审计。Fiat–Shamir 让两者在随机预言机模型下等价。
✕「复杂性理论只是理论，对调参没用。」
✓
它决定了哪些优化是可能的。比如「证明大小能不能做到 O(1)」这个问题， 答案依赖底层假设；不理解理论，就会在不可能的方向上浪费时间。
