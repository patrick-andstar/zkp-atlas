可信设置仪式：怎么让一群陌生人共同销毁一个秘密

KZG 需要一组长得像 [τ⁰]₁, [τ¹]₁, … 的公共参数，而 τ 必须没人知道。 问题是：总得有人生成它。仪式解决的就是这个矛盾 —— 把「相信一个人」变成「相信八十个人里至少有一个没撒谎」。

信任模型核心 ≈ 16 min 难度 3 / 5 前置：多项式承诺 产出：可复用的 .ptau

01为什么必须有这么一场仪式

KZG 的承诺是 C = [p(τ)]₁。要让这个式子有意义，必须有人算出 [τ⁰]₁, [τ¹]₁, …, [τᵈ]₁ —— 而算这些的前提是知道 τ。

矛盾出现了：

  • 算参数的人必须知道 τ；
  • 但任何人都不能知道 τ，否则能伪造证明。

解决办法是：算完立刻销毁。但「我删了」这句话没有任何说服力 —— 内存快照、swap、磁盘残留、甚至一张照片都可能是泄露渠道。

i
仪式的核心思路：把风险切成 N 份

不让一个人生成 τ，而让 N 个人接力。每个人只贡献自己那一段随机性， 然后销毁。最终 τ = τ₁·τ₂·…·τₙ。 只要有任何一个人真的销毁了，就没有人知道完整的 τ。

02参与者视角：一次完整操作

1

下载上一轮的参数

从公开地址取回 .ptau 文件，并核对它的哈希与上一轮公布的一致。

2

生成自己的熵

用本地硬件随机数、键盘敲击、甚至掷骰子，生成一段 τi。 关键是不能在任何联网设备上生成。

3

在隔离环境里更新参数

用离线机器（或者干脆断网）跑仪式程序，把 τi 混入参数。 计算过程会持续几分钟到几小时，取决于参数规模。

4

发布新参数和证明

输出新的 .ptau 和一个 attestation（证明这次更新正确执行）。 上传到公开地址。

5

销毁

这一步是全部安全性所在。 关机、拔电、物理销毁存储介质，或者用新随机数据覆写整个磁盘。 「删文件」不算销毁。

!
销毁失败的几种真实方式

① 用了带休眠功能的笔记本，内存被写进磁盘；
② 虚拟机快照被云厂商保留；
③ 程序把 τ 写进了日志文件；
④ 生成熵的过程中有屏幕录制或摄像头。

这就是为什么严肃的仪式要求「专用机器 + 物理销毁」。

031-of-N 的数学：为什么这样就安全了

每一轮的操作本质上是把参数「乘上」自己的秘密：

[ τk ]1  ⟶  [ ( τ · τi )k ]1 第 i 个参与者把自己那一段乘进去，得到新的一组参数

经过 N 轮之后：

τfinal = τ1 · τ2 · ⋯ · τN 每个参与者只知道自己的 τᵢ，以及「别人也乘了东西」这件事

关键论证：如果第 i 个参与者诚实地销毁了 τi， 那么任何人都无法从公开参数中恢复 τfinal —— 因为这等价于在不知道一个随机因子的情况下解出乘积。

攻击者控制的人数能否恢复 τ说明
0 个不能全部诚实
N−1 个不能只要剩 1 个诚实，乘积就未知
N 个能全部串通，安全性归零
✓
这就是「1-of-N 信任模型」

你不需要信任任何特定的人，只需要相信「这 80 个人里至少有一个不是骗子、 而且他的电脑没被入侵」。这个假设比「相信某个公司」弱得多。

04怎么验证一场仪式没被动手脚

仪式的价值在于可公开验证。如果只能「相信组织者」，那它就退化成单点信任。

每一轮的 attestation 包含：

内容作用
上一轮参数的哈希证明「我是基于正确的前序状态算的」
本轮参数的哈希供下一轮核对
配对等式证明证明更新确实形如 [τk] → [(ττi)k]，而不是随便换了一组点
参与者的公钥签名绑定身份，事后可追责（虽然无法撤销）

验证者只需要跑一条命令，就能检查整条链：

snarkjs powersoftau verify pot28_final.ptau

它会逐一验证每一轮的配对等式和哈希链接。任何一轮造假，都会在这里暴露。

i
但验证不了「销毁」

这是仪式的根本局限：数学只能证明「参数算对了」，不能证明「秘密删掉了」。 后者是一个物理/管理问题，只能靠流程设计（隔离机器、多人见证、物理销毁）来降低风险。

05真实案例：三次值得记住的仪式

仪式时间规模与结果
Zcash Sprout2016 6 人参与。后来发现实现有问题，理论上 toxic waste 可能被恢复，促成了 Sapling 重做
Zcash Sapling2017 90+ 人，使用改进后的协议（BCTV14 漏洞已修复）。成为行业标杆
Perpetual Powers of Tau2019 起 80+ 轮，产出支持到 2²⁸ 约束的通用参数，被大量项目复用

Sprout 的故事尤其值得记：它的参数生成用了当时最先进的方案， 但后来发现「参数格式本身」允许在某些条件下恢复 τ。 这说明仪式的安全性不只取决于参与者，还取决于协议的数学实现。

!
一个反直觉的事实

参与者越多，仪式越慢、越难组织，但安全性提升是边际递减的： 从 1 人到 10 人，风险降了 10 倍；从 80 人到 90 人，几乎没区别。 所以主流仪式规模停在几十到一百人，不是技术限制。

06风险清单：可能出问题的地方

风险后果怎么降低
销毁不彻底参与者可伪造任意证明专用离线机器 + 物理销毁 + 多人见证
实现有 bug秘密以非预期方式泄漏使用经过审计的客户端；事后公开源码
参与者被胁迫同上匿名参与（只公布公钥）；分散地理分布
「假装参与」实际只有少数人真正贡献公开 transcript + 独立验证
参数被替换验证密钥与电路不匹配核对最终哈希 + 重新编译电路比对

使用者该怎么核查一个项目的仪式

  1. 最终 .ptau 的哈希是否公开、是否被多个独立方复现？
  2. 每一轮的 attestation 是否可下载、能否通过 verify？
  3. 参与名单是否公开（哪怕只有公钥）？有没有独立机构参与？
  4. 电路源码是否开源，能否自己编译出同样的 r1cs？

四条里缺任何一条，你都在信任一群没有露面的陌生人。

07小结与常见误区

你应该带走的

  • 可信设置要生成 τ 的幂，而 τ 必须被销毁。
  • MPC 仪式把 τ 拆成 τ₁·τ₂·…·τₙ，只要一个诚实就安全。
  • 参与者流程：下载 → 生成熵 → 更新 → 发布 → 物理销毁。
  • transcript 可以验证「算得对」，但验证不了「删得干净」。
  • Zcash Sapling（90 人）和 Perpetual Powers of Tau（80+ 轮）是两个标杆。
✕「有可信设置就说明这个项目有后门。」
✓
可信设置是公开宣称的信任假设，后门是隐藏的。 真正该问的是：仪式是否可验证、参与者是否分散、参数是否被复用审计。
✕「只要参与者足够多就一定安全。」
✓
如果所有人用的都是同一个有 bug 的客户端，人再多也没用。 实现正确性优先于人数。
✕「Groth16 的仪式一次就够，所有电路通用。」
✓
Groth16 是电路专用的：改一行电路就要重跑 phase 2。 只有 PLONK 那类通用设置才能一次仪式服务所有电路。
✕「用了 STARK 就完全不用信任任何人。」
✓
STARK 不需要可信设置，但仍需信任哈希函数和实现正确性。 「透明」指的是参数生成透明，不是「零信任」。
